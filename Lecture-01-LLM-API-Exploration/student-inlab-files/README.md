# Exercise 1 — Exploring an LLM API Through Swagger

## Purpose

In this individual API exploration exercise, you will follow one interaction
through:

`Swagger → HTTP request → LLM messages → generated response`

You will inspect message roles, temperature, token usage, latency, response
metadata, and the boundary between caller-controlled and server-generated data.
The FastAPI application is already complete; your task is to investigate it
systematically through Swagger.

## Learning outcomes

By the end of the lab, you should be able to:

1. Distinguish an HTTP API from the model behind it.
2. Identify system, user, and assistant messages.
3. Explain what model and temperature fields control.
4. locate generated output, token usage, finish reason, and latency.
5. Recognize which request fields are controlled by the API caller.
6. Compare repeated API responses without changing multiple variables at once.

## Setup

Create and activate a virtual environment:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
```

Start the application:

```powershell
uvicorn main:app --reload
```

Open:

```text
http://127.0.0.1:8000/docs
```

Use `GET /health` first. The default backend is `mock`, so the lab runs without
an API key. The mock backend is only for learning the request flow; its token
counts are word-based approximations.

## Part A — Predict before executing (10 minutes)

Examine the sample `POST /chat` request without executing it. Individually
predict the method, endpoint, message roles, model, temperature, and likely
response fields. The TA will discuss the answers orally.

## Part B — Inspect the normal request (10 minutes)

1. Expand `POST /chat`.
2. Select **Try it out**.
3. Use the example request.
4. Select **Execute**.
5. Identify the request and response fields before moving to the experiments.

Do not focus only on the generated sentence. Inspect the HTTP method, endpoint,
request body, response body, status code, usage information, and metadata.

## Part C — Controlled experiments (15 minutes)

Change only one field at a time.

### Experiment 1: User-message constraint

Replace the user message with:

```text
Explain how an LLM generates its next token in exactly 15 words.
```

### Experiment 2: System-message audience

Keep the user message fixed and replace the system message with:

```text
Explain concepts to a person with no computer science background.
```

### Experiment 3: Temperature

Send the same messages at:

- `0.0`
- `0.7`
- `1.5`

Run each temperature twice. A low temperature often reduces variation, but it
does not guarantee identical output on every model or provider.

### Experiment 4: Few-shot format

Add an assistant message before the final user message:

```json
{
  "role": "assistant",
  "content": "Definition: ...\nAnalogy: ...\nLimitation: ..."
}
```

Then ask:

```text
Explain a context window using the same format.
```

Observe and discuss the differences.

## Part D — Identify the application boundary (5 minutes)

Answer:

1. Which values can the Swagger user directly change?
2. Which values are generated by the backend or model?
3. Why is the system message not secret when the API accepts it from the user?
4. Which fields should a production developer control server-side?

This is an introduction to the attack surface, not a jailbreak exercise. Do not
attempt to access external systems, real secrets, or other users' data.

## Part E — Compare through a second endpoint (15 minutes)

Open `POST /compare`. This endpoint holds the model and messages constant while
the server runs temperatures `0.0`, `0.7`, and `1.5`.

1. Read the request schema before executing it.
2. Predict the response structure.
3. Submit the same messages used in Experiment 3.
4. Confirm that the response contains exactly three results.
5. Compare response text, latency, and token usage.
6. Explain why this endpoint supports a fairer comparison than manually
   changing several request fields.

You are exploring the behavior of an existing API. You are not expected to edit
the FastAPI source code.
